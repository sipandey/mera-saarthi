# EP-04 production readiness — research

**Date:** 5 Oct 2026
**RPI stage:** Research
**Scope:** MS-02 approval gates, MS-12 evidence upload/review, MS-13 optional photos.

## Product/source findings

- The owner flow supports required Aadhaar and selfie evidence, required per-vehicle RC/insurance/PUC, plus optional vehicle photos. It has upload/replace, expiry entry, and a separate driver-photo consent switch.
- Admin can inspect short-lived links, approve/reject individual documents, approve drivers/vehicles only when required evidence is current, and block accounts/vehicles. Demo paths simulate metadata and review state only; they cannot prove camera, file transfer, Storage policy, RLS, or signed links.
- The migrations fail closed: existing owners/vehicles start pending, and SQL approval, availability, listing, and booking paths check document requirements. The optional-photo migration protects display access separately from required-document eligibility.
- Application code uses 30-second polling, not Supabase Realtime subscriptions. For the pilot this means state converges on refresh/poll; admin decisions are not pushed instantly to every open client.
- Code inspection found two client-side ordering/scope inconsistencies: a demo owner could see the newest identity evidence from a different fixture owner; some helpers did not use the SQL `created_at DESC, id DESC` tie-breaker. These can misstate readiness in the UI even though the server gate remains authoritative.
- Expo ImagePicker is used for selfie capture and vehicle-photo selection, but the app config had no explicit image-picker permission strings or microphone opt-out.

## Deployment constraints

- Supabase CLI is installed, but this environment has no Supabase access token; `supabase projects list` returns `AccessTokenRequiredError`.
- Docker is not running, so local Supabase reset/migration validation cannot be performed here.
- No disposable staging project is available. The organization is on Free, and creating preview branches can incur usage charges.
- Applying the timestamped migrations in the dashboard would bypass the normal migration workflow. The existing manually applied base schema has no baseline entry in migration history, so `db push` must not be run blindly. First adopt/pull the live schema into tracked migration history, compare it with the checked-in baseline, and validate the full migration chain in an isolated project.
- The product owner has designated an existing account as the initial administrator; resolve it to an auth/profile ID and promote it through a reviewed, auditable admin provisioning path. Do not store the phone in product docs or logs.

## Privacy and retention recommendation

Indefinite retention of raw Aadhaar, selfie, RC, insurance, PUC, and vehicle-photo files is not a privacy-minimizing default. The proposed product default, pending operator/legal approval, is:

1. For Aadhaar/selfie used only for manual identity review, retain the raw file through the final decision plus a 30-day appeal window, then purge the Storage object. Preserve only the current approval metadata needed to enforce the active decision (type, status, expiry, creation time); a new verification request requires fresh evidence.
2. Delete rejected or superseded files 30 days after the final decision/replacement, allowing a bounded appeal/recovery window. Retain reviewer ID, review timestamp, and rejection reason for up to one year after raw-file purge, then scrub those fields. Keep only status/type/expiry/creation metadata needed by active booking gates. Never copy Aadhaar UID into metadata.
3. Delete expired insurance/PUC/RC files 30 days after expiry. The latest approved expiry/status metadata may remain to fail closed; replacing evidence starts a new review.
4. A selfie used as the driver's display photo is retained only while the owner remains active and has display consent enabled; turning consent off makes it ineligible immediately and starts the same 30-day purge window. An optional vehicle photo is retained only while the owner keeps that photo active; explicit removal or replacement begins the 30-day purge window. A new photo cannot be withdrawn from the purge queue once the deletion worker has claimed it; the owner must upload fresh evidence to display a photo again.
5. Account inactivity does not by itself justify indefinite retention. Set a documented inactivity cutoff and deletion process before public collection; provide notice/consent and a way to request deletion. The local migration queues raw evidence when a profile or vehicle is deleted, after which cascading account deletion removes remaining verification metadata. A user-facing closure path, queue survival through actual auth/profile deletion, and an inactivity cutoff are not implemented yet.

This is an engineering recommendation, not legal advice. Aadhaar file collection for manual review is not UIDAI Aadhaar authentication. Obtain privacy/legal review on the collection purpose, notice/consent, retention, deletion, and any UIDAI-specific obligations before collecting real identity documents. References: [UIDAI Authentication Requesting Agency](https://uidai.gov.in/hi/authentication-requesting-agency), [UIDAI OVSE](https://www.uidai.gov.in/mr/ovse), [DPDP Act 2023](https://www.meity.gov.in/static/uploads/2024/02/Digital-Personal-Data-Protection-Act-2023.pdf), [DPDP Rules 2025 Gazette](https://www.meity.gov.in/static/uploads/2025/11/53450e6e5dc0bfa85ebd78686cadad39.pdf), and [DPDP Rules explanatory note](https://www.meity.gov.in/writereaddata/files/Explanatory-Note-DPDP-Rules-2025.pdf).

## Conclusion

EP-04 is substantially implemented in source and demo flows. A local retention migration and Edge Function implement the proposed raw-file purge; the worker is not deployed or scheduled. This configured production project cannot currently run EP-04: required schema, Storage bucket/policies, review RPCs, and migrations are absent. Before live collection, approve the retention policy, validate the full SQL chain and private Storage behavior in an isolated project, reconcile the existing base schema with migration history, configure/seal the worker schedule, then apply with authenticated CLI access and provision the named admin account. Demo-mode evidence is not production acceptance evidence.

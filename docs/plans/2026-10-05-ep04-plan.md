# EP-04 production readiness — implementation and release runbook

**Date:** 5 Oct 2026
**RPI stage:** Plan / release runbook
**Goal:** Run driver and vehicle verification with server-enforced booking gates, private evidence, auditable admin review, and an operational evidence-retention process.

## Current state and release decision

The owner/admin/client paths, four EP-04 and booking migrations, and a fifth local retention migration exist. The project also has a manually applied base schema in `supabase/schema.sql`, but no tracked baseline migration. Read-only inspection found the configured Supabase project is Production, its migration ledger is absent, and the four existing migrations are pending. This checkout did not have Supabase CLI authentication, Docker, or an isolated project at the time of inspection. The production database has not been changed by this work.

The retention worker is local source only. Account closure UI, an inactivity cutoff, first-admin bootstrap, staging validation, production migration reconciliation, function deployment, and Android live validation remain release gates. Do not collect real identity files or enable real bookings until all go/no-go checks below pass.

## Required policy decisions

Record the decisions in the product privacy notice and operating procedure before enabling uploads:

1. Approve or replace the proposed retention windows: raw approved/rejected/superseded evidence is queued for deletion 30 days after decision, replacement, expiry, or photo withdrawal; reviewer ID, decision time, and rejection reason are scrubbed 365 days after raw-file purge. Current status/type/expiry/creation fields remain while needed for active booking eligibility.
2. Define the account-inactivity cutoff, the user-facing account-closure/request-deletion route, deletion completion target, exception handling, and the owner accountable for the purge queue.
3. Approve the collection purpose, Aadhaar handling, notice/consent text, access roles, incident response, support/recovery route, and retention/deletion policy with the responsible privacy/legal reviewer.
4. Approve the project owner, billing tier, backup/restore plan, and a staging project. Do not create a billable project or preview branch without cost approval.

## Step-by-step production readiness

### 1. Freeze real collection and capture the release target

1. Keep real document uploads and production booking launch disabled. Use synthetic evidence only during implementation and staging validation.
2. Record the exact Production project ref, current Supabase plan, app environments, operator contacts, privacy decisions above, and approved release window in the internal operations record. Keep access tokens, database passwords, service-role keys, the retention secret, and identity documents out of Git, this plan, and chat.
3. Assign one operator to run each migration deployment. Do not run `supabase db reset` against Production; that command destroys the linked database when used with `--linked`.

### 2. Prepare a reproducible local database

The existing `supabase/schema.sql` is the one-time base schema required by the first incremental migration. Make it part of migration history before trying to build a clean database:

1. Add `supabase/migrations/20260930000100_initial_schema.sql` as an exact reviewed copy of `supabase/schema.sql`. Keep the existing five incremental migration files in timestamp order:
   - `20261001000100_booking_lifecycle_statuses.sql`
   - `20261001000200_pilot_booking_workflows.sql`
   - `20261003000100_driver_vehicle_verification_documents.sql`
   - `20261003000200_optional_public_vehicle_photos.sql`
   - `20261005000100_verification_evidence_retention.sql`
2. Add `supabase/migrations/20261005000200_initial_admin_bootstrap.sql` with the narrowly scoped first-admin bootstrap described in Step 6. This migration must be part of the tested chain before any Production admin is provisioned.
3. Resolve any duplicate-object statements or ordering assumptions in the tracked chain, then review the full baseline and all six incremental migrations together. Do not change the Production database to make the baseline apply there.
4. Install/use the repository-supported Node version, Docker, and current Supabase CLI. From the repository root run:

   ```sh
   npx supabase --version
   npx supabase start
   npx supabase db reset
   npx supabase db lint --local --fail-on error
   npm run typecheck
   ```

5. Confirm a clean reset builds the full schema and private `verification-documents` bucket. Inspect RLS, grants, triggers, functions, indexes, constraints, and booking-listing SQL after reset. Fix failures in migrations, then repeat the clean reset and lint.

### 3. Create and validate an isolated staging environment

1. Create or select a Supabase staging project with an approved cost and access policy. Do not copy production Aadhaar, selfies, RCs, insurance, PUC, or vehicle photos into staging.
2. Authenticate and link explicitly to staging; use its ref, never rely on whichever project happens to be linked:

   ```sh
   npx supabase login
   npx supabase projects list
   npx supabase link --project-ref <STAGING_PROJECT_REF>
   npx supabase migration list
   npx supabase db push --dry-run
   npx supabase db push
   npx supabase db lint --linked --fail-on error
   ```

3. Review the dry-run output before applying. On a fresh staging project it must show the baseline followed by all six incremental migrations. Never use `--include-seed` with Production.
4. Use the Supabase Dashboard for the staging project to add `VERIFICATION_RETENTION_SECRET` under **Edge Function Secrets**. Generate a unique staging-only value in the approved password manager; do not paste it into chat, a ticket, shell history, or source code. Then deploy the retention function:

   ```sh
   npx supabase functions deploy purge-verification-files --project-ref <STAGING_PROJECT_REF>
   ```

   Confirm `supabase/config.toml` leaves `verify_jwt = false` only for this function; its dedicated secret header is the function authentication.
5. Use the reviewed bootstrap function to promote a synthetic staging account. Confirm that the account can sign in and perform admin review before running the staging acceptance scenarios.

### 4. Pass the staging acceptance scenarios

Use synthetic accounts and files. Record the result, project ref, migration list, and operator for each scenario.

1. Create customer, owner, and admin accounts. Confirm ordinary users cannot self-assign admin or approve documents.
2. Submit Aadhaar and selfie for a driver, then RC, insurance, and PUC for a vehicle. Confirm they are private, pending documents and the driver/vehicle cannot appear in customer search or accept a booking.
3. As admin, reject a document without a reason and confirm the server rejects that action. Reject with a reason and confirm the owner sees the correct status/reason. Upload a replacement and confirm the old decision cannot satisfy the latest-evidence gate.
4. Approve only current required documents; confirm the driver/vehicle approval controls are unavailable until every required document is current and approved. Confirm expired insurance/PUC and changed registration details fail closed and require review again.
5. Attempt listing and booking through the app and direct authenticated API/RPC calls for pending, rejected, expired, blocked, and missing-document accounts/vehicles. Every attempt must be denied server-side.
6. Verify Storage access as owner, unrelated owner, customer, admin, and anonymous user. Owners may access only their own evidence; admins may review; customers and anonymous users must not read Aadhaar, RC, insurance, or PUC. Customer photo access must be limited to the current approved selfie/vehicle photo, explicit driver-photo consent, an eligible vehicle, and short-lived links.
7. Confirm selfie display consent and vehicle photos are optional presentation choices and never affect booking eligibility. Withdraw an optional vehicle photo and driver display consent; verify the display stops immediately and purge becomes eligible after the retention interval.
8. In staging only, make synthetic rows eligible for rejected, replaced, expired, withdrawn-photo, and consent-withdrawn purge. Invoke the worker; verify deletion through Storage API, `purged_at`, nullable `storage_path`, retry behavior, and the eight-attempt attention path. Verify active approval metadata remains sufficient for booking checks after raw-file purge and old review metadata is scrubbed after its window.
9. Exercise profile/vehicle deletion and verify queue records survive long enough to remove raw objects. Confirm the account-closure request path and inactivity policy once implemented; until then these remain explicit launch blockers.
10. Test application refresh, sign-out/sign-in, poor network, upload failure/retry, signed URL expiry, Android camera/gallery permission prompts, and owner/admin/customer screens on supported physical Android devices.

### 5. Make migration history safe for the existing Production database

Supabase migration repair changes only the migration ledger; it does not execute migration SQL. Repair history only after independently proving that the corresponding schema is already present. See [Supabase database migration guidance](https://supabase.com/docs/guides/deployment/database-migrations) and the [CLI migration reference](https://supabase.com/docs/reference/cli/supabase-migration-list).

1. Confirm a current restorable Production backup exists in the Dashboard and record how to restore it. Confirm the project ref with a second operator.
2. Authenticate using an authorized operator account and link explicitly to Production:

   ```sh
   npx supabase login
   npx supabase link --project-ref <PRODUCTION_PROJECT_REF>
   npx supabase migration list
   npx supabase db dump --linked --schema public,storage -f /private/tmp/mera-saarthi-production-before-ep04.sql
   ```

3. Compare the live dump with the intended initial state in `supabase/schema.sql`, including custom policies/functions and the `storage` bucket/policies. Document every difference. The expected state is that only the base schema exists; the four earlier migrations and the retention migration have not been applied. If the live state differs, stop and write/review a corrective migration before continuing.
4. Only after exact baseline equivalence is confirmed, record the baseline migration as already applied:

   ```sh
   npx supabase migration repair 20260930000100 --status applied
   npx supabase migration list
   npx supabase db push --dry-run
   ```

   The dry run must list exactly the six incremental migrations, in timestamp order, and no baseline replay. If it lists anything else, stop and reconcile the state; do not use `--include-all` as a shortcut.
5. During the approved release window, with backup and rollback operator present, apply the six reviewed migrations:

   ```sh
   npx supabase db push
   npx supabase migration list
   npx supabase db lint --linked --fail-on error
   ```

   Confirm the remote ledger shows baseline plus all six migrations and query the deployed policies, functions, triggers, bucket settings, and active admin count before proceeding. If any migration fails, stop; do not mark it applied with `migration repair` unless the SQL has actually completed and the resulting schema has been independently verified.

### 6. Provision the initial administrator

The existing privilege trigger requires an administrator to change a profile role, so it does not yet provide a safe first-admin path. The `20261005000200_initial_admin_bootstrap.sql` migration described in Step 2 must be implemented and validated before Production provisioning:

1. Add a `SECURITY DEFINER` bootstrap function restricted to `service_role`, with a fixed safe `search_path`. It must fail if any admin already exists, require an existing Auth user/profile, verify the target identity against the owner-approved phone at runtime, and promote exactly that profile within one transaction. Do not hardcode the phone number in migration source, logs, or product docs.
2. Permit this narrowly scoped service-role bootstrap through the profile privilege trigger, without relaxing authenticated-user checks or enabling self-promotion. Revoke execute from `public`, `anon`, and `authenticated`; grant only to `service_role`. Add audit evidence for the target account and operator without storing Aadhaar or the phone in application telemetry.
3. Run the bootstrap in staging and prove: the approved target becomes the sole admin; wrong identity, nonexistent profile, repeat invocation, and ordinary-user invocation fail; a second profile cannot self-promote.
4. Confirm the reviewed bootstrap migration is applied in staging and Production before calling the initial-admin operation. In Production, resolve the already-created Auth user to its UUID using the dashboard, run the bootstrap once through an authorized server-side/service-role operator path, then verify the account can sign in and review a synthetic pending item. Never place the service-role key in the mobile app.

### 7. Deploy and schedule the production retention worker

1. Generate a new high-entropy Production-only secret and add it under **Edge Function Secrets** in the Supabase Dashboard. Never reuse the staging secret:

   ```sh
   npx supabase functions deploy purge-verification-files --project-ref <PRODUCTION_PROJECT_REF>
   ```

2. Enable `pg_cron`, `pg_net`, and Vault for the project after confirming availability on the selected plan. Store the project function URL and the same secret in Vault. Use the reviewed schedule SQL in [`supabase/functions/purge-verification-files/README.md`](../../supabase/functions/purge-verification-files/README.md) to invoke the function daily at 02:15 UTC. Keep the job disabled until privacy/operator approval, staging validation, and Production migration completion.
3. Invoke the function once manually with no eligible real evidence. Confirm a successful response, then enable the cron job. Verify its first scheduled run in Cron/`pg_net` logs.
4. Set an operational alert for function 502 responses, queue rows at eight attempts, and missed scheduled runs. Assign an operator to inspect/retry failures. Deletes must go through the Supabase Storage API; do not delete objects by editing `storage.objects` directly. See [scheduled function guidance](https://supabase.com/docs/guides/functions/schedule-functions), [function secrets](https://supabase.com/docs/guides/functions/secrets), and [Storage deletion](https://supabase.com/docs/guides/storage/management/delete-objects).

### 8. Configure and validate the app against Production

1. Set the Production Supabase URL and publishable/anon key in the approved Expo/EAS environment. Keep database passwords, service-role keys, and retention secrets out of `EXPO_PUBLIC_*` variables and all client builds.
2. Build a release Android app from the reviewed branch. Sign in as customer, owner, and the provisioned admin. Use test accounts and synthetic documents until the final go-live approval.
3. Repeat the core owner upload → pending review → admin decision → owner sees status → eligible supply becomes bookable flow against Production. Confirm missing/pending/rejected/expired evidence cannot be listed/booked, and approved current evidence can. Confirm every direct API bypass scenario still fails.
4. Verify Storage privacy, signed-link expiry, photo withdrawal, retention worker monitoring, crash/error reporting, support contact, and the account-closure request route. Do not launch until the account-closure and inactivity decisions in Required policy decisions are implemented and exercised.

### 9. Go live and operate

1. Hold a release review with engineering, operations, privacy/legal owner, and the Production operator. Check all gates below and record sign-off.
2. Enable real document collection for a small, invited pilot cohort. Monitor upload/review queue age, booking denials, purge queue, worker health, unauthorized-access logs, and support requests daily.
3. Reconcile incidents and retention jobs weekly during the pilot. Review admin access regularly; revoke access immediately when an operator leaves. Keep a documented incident path for exposed identity documents and suspected account compromise.
4. Expand the cohort only after the pilot demonstrates successful reviews, no server-gate bypass, private file access, functioning deletion, and reliable recovery.

## Go/no-go checklist

Production is ready only when every item is true:

- [ ] The privacy/retention decisions, inactivity cutoff, account-closure route, notice/consent, incident contact, and support/recovery procedure are approved and published.
- [ ] The tracked baseline plus all incremental migrations reset cleanly in local Supabase; SQL lint and application typecheck pass.
- [ ] All positive and negative staging scenarios pass, including direct API bypass, RLS/Storage isolation, replacement/expiry, photo consent, and purge retry behavior.
- [ ] Production backup/restore procedure is confirmed; live schema is compared to the baseline; migration history shows the baseline and all deployed migrations without replay or unexplained drift.
- [ ] The initial admin was provisioned through the reviewed one-time bootstrap and ordinary users cannot self-promote.
- [ ] Production Edge Function secret is unique and private; function deployment, Vault/Cron schedule, alerts, and first run are verified.
- [ ] Release Android build uses only public client credentials; physical-device upload, review, booking gates, and recovery flows have been exercised.
- [ ] Operations owns the pending-review queue, purge failures, account deletion requests, access review, and incident response.

## Implementation status

Local source implements deterministic latest-evidence selection, purpose-specific photo/camera permissions, private evidence review, optional photo display/withdrawal, and a purge migration/worker. The baseline migration and first-admin bootstrap are not implemented yet. The worker is not deployed or scheduled. Production rollout remains blocked until the steps above are completed with authenticated Supabase access and an isolated staging environment. Demo-mode evidence demonstrates local state and presentation only; it is not acceptance evidence for Supabase security or Production operations.

# EP-05 Stand Operations — RPI implementation note

**Date:** 5 Oct 2026
**RPI stage:** Research → Plan → Implement
**Scope:** Complete the code portion of MS-08 by surfacing recorded booking lifecycle history to admins and demonstrating the same workflow in demo mode.

## Research

- EP-05 contains MS-06 availability/hours, MS-08 admin safety and booking controls, and MS-10 pilot metrics.
- MS-06 and MS-10 have app/schema implementations; remaining work is timezone/device rollout validation, analytics collection/retention policy, and success thresholds.
- MS-08 already supports account/vehicle blocks, reasoned booking transitions, and database history in `booking_status_history`. The admin screen showed current booking state and reason but did not read or render the history table.
- The existing history table has an admin-readable RLS policy. The app should load history only for admins, display it only in the admin surface, and avoid a second source of audit records.
- A support owner/contact and incident escalation procedure are not configured. The UI must not invent a phone number or claim an incident workflow exists.

## Plan and acceptance

1. Fetch the existing status-history rows for bookings already loaded by an admin. Acceptance: each row includes status transition, reason, actor label, and timestamp; user-facing owner/customer screens do not show the admin timeline.
2. Render a compact newest-first timeline beneath each admin booking. Acceptance: old transitions remain distinguishable from current status; missing history has an honest empty state.
3. Record demo request creation and each local state transition in synthetic history. Acceptance: a user can create a demo booking, switch through owner/admin roles, and inspect the matching sequence without synthetic records being sent to Supabase.
4. Update backlog/current-state/demo docs and the agent decision log. Leave support contact/incident response as an explicit release decision.

## Implemented locally

- `src/cloudData.ts` reads status history only in admin mode and only for the loaded bookings.
- `src/screens/AdminScreen.tsx` sorts history by event time and displays the newest ten events per booking, with localized status/reason text, timestamp, and actor name where available.
- Demo booking creation and subsequent transitions append synthetic local history entries; cloud records remain server-authored.
- English/Hindi copy and EP-05 product notes are updated.

## Validation and remaining rollout

- `npm run typecheck` passes.
- `git diff --check` passes.
- No staging project or Android device was exercised in this implementation turn. Before pilot use, run this validation sequence on a disposable Supabase project and supported Android build:
  1. Apply the tracked base schema and migrations to the disposable project, create separate admin, owner, and customer accounts, and confirm only the intended account has the admin role.
  2. As the customer, create a booking. As the owner, accept it; then exercise a reasoned cancellation, rejection, no-show, or completion using valid lifecycle transitions.
  3. Refresh as admin and confirm each booking timeline shows the creation event and every committed transition, newest first, with the expected status, reason, actor, and timestamp. Repeat in Hindi and with a history longer than ten events.
  4. As owner and customer, attempt both the app path and direct Supabase reads of `booking_status_history`; confirm the table policy denies access and the admin timeline is absent from their screens.
  5. In demo mode, create and transition a booking, switch roles, restart the app, and confirm the synthetic timeline persists locally and never appears in Supabase.
  6. On Android, review narrow-width wrapping, scroll behavior, and long actor/reason labels. Record results and any fixes before enabling the pilot.
- The admin view currently loads the booking history for the set of bookings returned by the existing unpaginated admin booking query. Add pagination or a bounded date window before pilot volume makes those result sets large.
- MS-08 remains partial until an actual support owner/contact and incident-escalation route are approved. MS-06 device/timezone validation and MS-10 data-retention/success thresholds remain operational rollout work.
